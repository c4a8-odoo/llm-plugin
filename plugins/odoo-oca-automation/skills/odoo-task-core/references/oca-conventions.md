# OCA conventions

Condensed from the OCA contribution guidelines (OCA/odoo-community.org, CONTRIBUTING.rst) and
the OCA/maintainer-tools wiki. When something here conflicts with the repository you are working
in, the repository wins; when in doubt, fetch the current guideline page.

## Module layout

```
<module>/
  __init__.py
  __manifest__.py
  README.rst                 generated, never edit by hand
  readme/
    DESCRIPTION.rst          required
    USAGE.rst  CONFIGURE.rst  ROADMAP.rst  HISTORY.rst  INSTALL.rst   optional
    CONTRIBUTORS.rst         names, one per line, add yourself/author when touching code
    CREDITS.rst              funders, other credits
  controllers/  models/  wizards/  reports/  views/  data/  demo/  security/  static/  tests/
  i18n/<module>.pot          generated by the OCA bot after merge, never commit translations by hand
  migrations/<version>/      pre-/post-migrate scripts for THIS version only
  static/description/icon.png
  static/description/index.html   generated from README fragments by oca-gen-addon-readme
```

Python files start with the copyright and license header, no encoding line:

```python
# Copyright 2026 <Author or Company>
# License AGPL-3.0 or later (https://www.gnu.org/licenses/agpl).
```

Use LGPL-3 only when the repo/module already does.

## Manifest

```python
{
    "name": "Partner First Name",
    "summary": "One sentence, no trailing period",
    "version": "19.0.1.0.0",
    "category": "Extra Tools",
    "website": "https://github.com/OCA/partner-contact",
    "author": "Original Author, Odoo Community Association (OCA)",
    "maintainers": ["github-handle"],
    "license": "AGPL-3",
    "development_status": "Beta",   # Alpha | Beta | Production/Stable | Mature
    "depends": ["base", "contacts"],
    "data": ["security/ir.model.access.csv", "views/res_partner_views.xml"],
    "demo": [],
    "assets": {"web.assets_backend": ["partner_firstname/static/src/**/*"]},
    "installable": True,
}
```

Rules: `author` ends with `, Odoo Community Association (OCA)`; `website` is the repo URL;
`version` is `<odoo>.<major>.<minor>.<patch>`; keep keys you actually use; `application` only
for real applications; `auto_install` only with a reason; no `description` key (README fragments
replace it); `installable: False` marks a module not yet migrated.

## Version bump rules

**The version bump happens at merge time, not in the PR.** The OCA merge bot bumps the manifest
`version` when a maintainer merges with `ocabot merge <patch|minor|major|nobump>`. A `[FIX]`,
`[IMP]` or `[REF]` PR therefore leaves `__manifest__.py` `version` untouched; a manual bump in
such a PR is a review remark ("drop the bump, the bot does it"), never a blocker. What the
contributor and reviewer decide is the **bump size**, stated in the PR body or review summary so
the merger picks the right command:

| change | bump size | OCA bot command at merge |
|---|---|---|
| bug fix, typo, test only | patch `x.y.z+1` | `ocabot merge patch` |
| new feature, new field without data migration | minor `x.y+1.0` | `ocabot merge minor` |
| data model change needing migration scripts, behaviour break | major `x+1.0.0` | `ocabot merge major` |
| README, translations, CI config | none | `ocabot merge nobump` |

Exceptions where the PR sets the version itself:

- `[MIG]` PRs set `"version": "<target>.1.0.0"` in the migration commit.
- PRs shipping `migrations/<version>/` scripts: the folder name must match the version the module
  will have, so the PR bumps the manifest to that version by hand and the merger uses
  `ocabot merge nobump`. Say so in the PR body.

When a major or minor change renames or removes fields/models, add
`migrations/<new version>/pre-migrate.py` / `post-migrate.py` using `openupgradelib` helpers.

## Commit messages

```
[TAG] module_name: short imperative summary

Optional body explaining why, not what. Wrap at 72 characters.
```

Tags: `[FIX]` bug fix, `[IMP]` improvement, `[ADD]` new module, `[REF]` refactor, `[REM]` removal,
`[MIG]` migration to a new Odoo version, `[I18N]` translations, `[REV]` revert. Several modules:
`[FIX] module_a, module_b: ...`. Never squash someone else's history; one logical change per commit.
Keep the `(cherry picked from commit <sha>)` trailer that `git cherry-pick -x` adds when porting.

AI attribution: when an AI assistant helped produce a commit, mark it with an `Assisted-by:`
trailer, never `Co-Authored-By:` (the author of record is the human; the assistant is not a
co-author). Put it last in the body, after any `(cherry picked from commit ...)` line:

```
[FIX] module_name: short imperative summary

Body.

Assisted-by: Claude <noreply@anthropic.com>
```

## Pull requests

Title: `[<version>][TAG] module_name: summary`, for example `[20.0][MIG] partner_firstname: Migration to 20.0`.

Body conventions:
- Describe the change and how to test it.
- Link issues with `Closes #123` or `Related to #123`; migration PRs say `Part of #<migration issue>`.
- Ports say `Forward-port of #<pr>` or `Backport of #<pr>` and list the ported PRs.
- Mention `@<maintainers>` listed in the manifest so they get pinged.
- Do not include security review content; that stays local.

Merge policy: two approvals from OCA members (one may be a maintainer), green CI, and a runboat
check when UI changes are involved. Automations never approve unless configured to, and never
issue `ocabot merge`.

## Code style

- pre-commit with the repo's config decides formatting (black/ruff, isort, prettier, pylint-odoo,
  flake8, eslint). Run `pre-commit run -a` before committing; do not argue with it in reviews.
- XML ids: `view_<model>_<type>` (`view_project_task_form`), actions `action_<name>`, menus
  `menu_<name>`, record rules `rule_<model>_<scope>`, groups `group_<name>`.
- Model files named after the model: `models/project_task.py` for `project.task`; one model per
  file; `_inherit` modules keep `_name` out unless creating a new model.
- Field `string` only when it differs from the auto-generated label; always wrap user-facing
  strings in `_()`; `_logger = logging.getLogger(__name__)`, never `print`.
- Tests under `tests/`, `from odoo.tests import TransactionCase` (or `HttpCase`), `setUpClass`
  with `cls.env = cls.env(context=dict(cls.env.context, tracking_disable=True))`, tagged
  `@tagged("post_install", "-at_install")` when they rely on other modules being installed.
- Views: no `attrs`/`states` from 17.0, `<list>` instead of `<tree>` from 18.0, `t-out` instead of
  `t-esc`/`t-raw` from 16.0.
- Access: every new model has lines in `security/ir.model.access.csv`; record rules in
  `security/<model>_security.xml`; `sudo()` only with a comment stating why it is safe.

## Branches and repositories

- Version branches `12.0` ... `20.0` are protected; work happens on fork branches and PRs.
- Each OCA repo has a pinned "Migration to version X.0" issue listing modules; claim a module
  there before migrating (full mode may comment; draft mode only notes it in the log).
- `oca-port` (pip package) is the recommended tool for migrations and for finding commits/PRs
  not yet ported between branches. `oca-gen-addon-readme` regenerates README.rst.
- Runboat (`https://runboat.odoo-community.org`) builds a preview for every PR; `gh pr checks`
  shows its status with the other CI checks.
